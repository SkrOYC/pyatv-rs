# Risk register

Distilled from the research corpus and live-device reports. Each risk names its severity, why it matters, and the concrete mitigation. Interoperability risks can produce incorrect bytes without an error until they reach a device, so they dominate this list. Review the register before changing a protocol.

## High severity

**H1 — HAP SRP M1 uses unpadded `H(g)`; RustCrypto `srp` hardcodes the padded form.** `Client::process_reply()` cannot be used for HAP pairing. Mitigation: call the crate's public low-level primitives and `srp::utils::compute_m1_rfc5054(..., g_no_pad = true, ...)` directly (documented in `crypto-pairing.md` §9). Back it with a known-answer test from a captured pairing before trusting it. If the low-level API proves fragile, fall back to hand-rolling SRP math against `srp` 0.6.

**H2 — `srp` may still be a 0.7 release candidate.** An RC's API is not frozen. Mitigation: pin the exact validated version; track `RustCrypto/PAKEs` for the 0.7 stable release; keep 0.6 as a fallback; do not upgrade without re-running the SRP known-answer tests.

**H3 — Three distinct ChaCha20 nonce layouts and per-channel HKDF salt/info strings.** A single wrong byte decrypts garbage in one direction with no parse error. Mitigation: implement each nonce construction as an explicitly parameterized type (zero-prefix width + counter width); copy the salt/info table from `crypto-pairing.md` §3 verbatim; unit-test each channel's key derivation against captured fixtures. Note the AirPlay event channel swaps read/write info strings.

**H4 — OPACK and Companion have no public spec and no Rust prior art.** pyatv's `opack.py` and `atvproxy` are the only ground truth, and pyatv's own OPACK implementation is explicitly incomplete for some types (e.g. absolute-time 0x06). Mitigation: hand-write OPACK in its own crate with exhaustive round-trip property tests including open-ended containers and back-references; validate against `atvproxy` captures; treat pyatv as an incomplete spec for the flagged types and reverse-engineer them directly.

**H5 — MRP-over-AirPlay tunneling changes across tvOS releases.** Modern tvOS carries MRP inside an AirPlay 2 data-stream channel. The transport abstraction and full MRP state machine work against tvOS 27. A 60-second run confirmed the two-second feedback loop and data channel. A 45-second run without feedback did not show a closure, but it sent no later control request and does not prove that feedback is optional. Mitigation: keep MRP transport-independent and capture an Apple controller before changing heartbeat or synchronization behavior.

## Medium severity

**M1 — Legacy AirPlay device-auth quirks must be replicated byte-for-byte.** The pair-setup IV last-byte `+1` increment, the doubled-SHA1 session key, the opaque trailing blob encrypted with the signature, and the Ed25519-seed-as-SRP-ephemeral reuse all diverge from textbook crypto and have no crate support. Mitigation: implement exactly as `crypto-pairing.md` §2.2/§5.4/§6 describes; do not "fix" the oddities; validate with a legacy-device capture. Lower severity than H-items because legacy AirPlay is old and may be deprioritized.

**M2 — prost compiles pyatv's proto2 corpus perfectly and then silently drops every `extend` block.** Resolved by a measured spike (`docs/research/mrp-protobuf-spike.md`, 2026-08-24) and closed in code. The compile half was never in doubt: prost-build 0.14.4 built all 77 vendored files with no errors, and protox 0.9.1 produced **byte-identical** output to protoc 35.1, so the toolchain is pure Rust and the crate builds offline with no `$PROTOC`. The real finding is the second half — prost has no concept of proto2 extensions at all (the word appears once in prost-build's source, in an unrelated doc comment) and its decoder discards unknown fields, so a decoded `ProtocolMessage` loses the payload with no error. Since every MRP message _is_ an extension, that would have produced a client that reads `type` and nothing else. Mitigation, implemented: `build.rs` walks the same `FileDescriptorSet` a second time and generates a typed handle per extension, and `src/protobuf/{wire,extensions}.rs` reads and splices the field directly on the serialised envelope, in ascending tag order so output stays byte-identical to the reference implementation. Eight known-answer vectors generated by pyatv's own protobuf runtime round-trip byte for byte. rust-protobuf 3.7.2 was spiked as the documented fallback and does support extensions natively; it was rejected on API and lint grounds, not capability — see the spike §5 if the decision ever needs revisiting. Two facts worth carrying forward: `mrp-companion.md` §1.3's claim that the extension field number equals the `Type` enum value is wrong for all 55 messages, and the `protobuf` 4.x line on crates.io is Google's separate project, not a rust-protobuf upgrade.

**M3 — Legacy AES-CTR semantics remain unverified against hardware.** Companion text replacement, append, clear, focus, and read-back passed against tvOS 27, so the RTI keyed-archive payload is live-verified. The legacy AirPlay `Ctr128BE<Aes128>` path still depends on known-answer tests rather than a legacy device capture. Mitigation: capture the AES-CTR exchange before changing its full-IV counter semantics.

**M4 — Custom AirPlay HTTP/RTSP codec is unavoidable and easy to get subtly wrong.** Reverse connections, single-socket dual roles, an event channel. Mitigation: sans-io `tokio_util::codec` with `Content-Length` buffering (`Ok(None)` on partial frames), round-trip tests, and capture-based tests; do not attempt to force reqwest/hyper.

**M5 — Dependency currency and the fast-moving dalek/RustCrypto stack.** `ed25519-dalek`/`x25519-dalek` bumped to 3.0.0 in a recent wave; the crypto set must co-resolve on one RustCrypto trait generation. Mitigation: the Step 0 scaffold validates co-resolution; re-verify versions and read full rustdoc at each phase; `cargo-deny` advisories + `cargo-machete` in CI; `cargo update` guarded by resolver v3 MSRV-awareness.

**M9 — tvOS 27 does not answer the open RAOP AirPlay 2 audio `SETUP`.** The Rust client completes HAP authentication and the event-channel setup, then times out waiting for the audio-stream `SETUP` response. pyatv `0.18.0` fails at the same request with the same credential and WAV, so this is a shared interoperability gap rather than evidence of a Rust-port regression. Mitigation: capture a successful Apple sender and compare its setup body, encryption material, and request order. Do not change the `shk` derivation from inference alone.

## Low severity / watch

**L1 — pyatv does not fully interoperate with tvOS 26 and later.** The live Rust probe reproduced upstream issue 2821: tvOS accepts `/play`, then returns `500 Internal Server Error` to `/playback-info` without fetching the media. The RAOP control also reproduced the Rust timeout at the same audio `SETUP` in pyatv `0.18.0`. Mitigation: use pyatv as the parity reference, but use successful Apple sender captures as the compatibility reference for these paths.

**L2 — Device-side revocation can remove stale credentials from a saved Rust configuration.** On-disk compatibility with pyatv is implemented and pyatv `0.18.0` loaded the Rust-written file. During the live pass, a normal reconnect after device-side controller removal rewrote the Rust test file without its stale credential fields. It is not known whether pyatv does the same. Mitigation: reproduce the flow with controlled file copies before classifying it as data loss or a parity divergence.

**L3 — RAOP uses PCM for pyatv parity.** Closed by exhaustive source inspection: pyatv never reads the advertised codec list and always sends PCM. The live RAOP failure occurs before audio negotiation completes and does not provide evidence for adding an ALAC encoder.

**L4 — Provisional MSRV (1.88).** Chosen for let-chains; a dependency may demand higher. **Verified 2026-08-25 and still holding:** `cargo check --workspace --all-features --locked` compiles clean on rustc 1.88.0 with the current lockfile, so no bump is needed. Mitigation: the `msrv` job in `.github/workflows/ci.yml` reads the floor out of `[workspace.package] rust-version` and builds against exactly that toolchain on every PR — it does not repeat the number, so the job and the manifest cannot drift. Note that `cargo msrv verify` is _not_ what runs there: cargo-msrv 0.19.3 looks for `package.rust-version` and cannot see `[workspace.package] rust-version` in a virtual manifest, so it fails at the workspace root before checking anything. It does work per member (`cargo msrv find --path crates/<name>`) and is in the devenv for exactly that job — finding a _new_ floor after a dependency bump. Bump deliberately with a version note (an MSRV bump is a minor-version change for a library).

**L5 — Point-in-time research.** All crate versions, star counts, and pyatv behavior were captured 2026-08-24. Mitigation: re-verify at the start of each phase; the reports cite their sources for exactly this reason.

**L6 — Do not implement FairPlay.** No open implementation exists; it depends on Apple hardware key material; pyatv only parses its advertisement. Mitigation: explicitly out of scope. Revisit only if a future feature genuinely requires classic encrypted RAOP, which would be net-new research with no precedent.

**L6 — Upstream discovery quirks are preserved deliberately, not fixed.** The Step 1 port keeps pyatv's observed behaviour where it looks like a bug, so that a real device sees the same traffic and the same config comes out: `create_service_queries` chunks questions with a 4-wide window on a 3-stride (duplicating boundary questions), `BaseService.merge` never updates port/identifier/pairing, Companion's `PAIRING_*_MASK` constants disagree with their own derivation comments, `DeviceInfo.operating_system` and `lookup_os` disagree on Gen2/Gen3, and the `"22J354": "17.0"` version-table entry is almost certainly a typo. Each is pinned by a test with a comment citing `docs/research/discovery-port-spec.md` §9. Mitigation: decide per item, with a device capture in hand, whether to keep or diverge — never silently.

**L7 — Multicast discovery is IPv4-only and interface enumeration is host-specific.** pyatv's multicast client joins `224.0.0.251` on every IPv4 interface via `netifaces`; the port uses `if-addrs` + `socket2`, which is enough on Linux/macOS but untested on Windows and skips IPv6 entirely, as pyatv does. Mitigation: the unicast path (`--scan-hosts`) is the fallback on any network where multicast misbehaves; revisit IPv6 only if a device is seen advertising AAAA-only.

**M6 — Stricter-than-pyatv pairing verification may reject a device pyatv accepts.** pyatv never checks the accessory's SRP proof (its `step2` compares a value with itself), never verifies the M6 / pair-verify M2 Ed25519 signatures, and never inspects the final state/error TLV (`docs/research/hap-pairing-port-spec.md` §8). The Rust port verifies all three, per the HAP specification, because a silent skip hides both wrong-PIN and man-in-the-middle failures. If a real device ever fails one of these checks where pyatv would proceed, treat it as a finding to capture with `atvproxy` — do not loosen the check blindly; add a documented per-check lenient option only against evidence.

**L8 — `srp` is a release candidate (0.7.0-rc.3) whose `g_no_pad` documentation is backwards.** Verified by a compiled probe (`docs/research/crate-verification-2026-08-24.md`): HAP needs `g_no_pad = true`, and `process_reply()` cannot be used because it hardcodes padded `g`. The port calls `srp::utils::compute_m1_rfc5054` directly and pins the behaviour with client↔server tests plus a fixed-seed KAT, so an rc→final API change will fail the build or the tests, never silently change the proof.

**M7 — AirPlay HAP pairing on this tvOS 27 device never displays a PIN (Companion does) — but the tunnel does not need it.** Observed 2026-08-24 against an Apple TV 4K gen 3 (`flags=0x18644`: HomeKit-pairing bit 0x200 set, PIN-required bit 0x8 clear): `/pair-pin-start` and pair-setup M1 both return 200 and M2 arrives, but no code appears on screen or in Settings → AirPlay and HomeKit. Our request bytes equal pyatv's, and pyatv's own troubleshooting page documents the same symptom, so this is device behaviour rather than a port defect. **Resolved as a blocker on 2026-08-24 by a live experiment** (`docs/research/airplay-tunnel-auth-experiment-2026-08-24.md`, reproducible via `crates/pyatv-proto-airplay/examples/airplay_verify_probe.rs`): the AirPlay endpoint accepts HAP pair-verify against the credentials from **any** completed HAP pairing on the device, including the Companion one. M1–M4 complete with `200`/`200`, the accessory's identifier and Ed25519 signature verify against the Companion-stored `atv_id`/`ltpk`, the `Control-*` transport keys work first try, and both `GET /info` and the `isRemoteControlOnly` `SETUP` succeed over the encrypted channel — confirmed twice, with this port's credentials and with pyatv's own. Transient pairing is _not_ an alternative here: `POST /pair-setup` with `X-Apple-HKP: 4` is refused `470 Connection Authorization Required` with an empty body, and a control run proved the refusal is about the transient branch rather than about the withheld `/pair-pin-start`. Mitigation, now concrete: Companion pairing (Step 3) remains the only pairing path on modern tvOS, and the facade must fall back to the Companion service's HAP credentials when the AirPlay service has none of its own — a deliberate divergence from pyatv's `extract_credentials`, which only ever reads the AirPlay service's own `credentials`. Keep the AirPlay pair-setup path (it is hermetically tested end to end) for earlier devices, and revisit with an `atvproxy` capture of an Apple sender if AirPlay-only devices need it. Explicit controller removal is verified: M2 still authenticates the device, then M4 returns `Authentication` for the removed controller. Residual risk is natural expiry of a cross-protocol pairing without user action.

**L10 — tvOS 27 sets `skipRecord=true` during AirPlay 2 setup.** The Rust client honored the key and completed a stable MRP tunnel. The `play_url` setup returned the same key, and the client again omitted `RECORD` before reaching the separate `/playback-info` failure. pyatv does not parse this key. Mitigation: continue to honor the explicit receiver value, treat an absent key as permission to send `RECORD`, and do not assume that `timingPort` is present.

**M8 — pyatv's OPACK encoder and decoder disagree on back-reference interning.** Found by a property test during the port: pyatv interns by encoded length on the pack side (`opack.py:129`) and by type on the unpack side (`opack.py:208-238`), so `pack([[1, 2], "a", "a"])` produces bytes pyatv's own `unpack` rejects. The Rust codec uses the decoder's rule on both sides — the side exercised against real devices — and reproduces every pyatv test vector byte for byte. Residual risk: a payload where Apple's decoder follows a third rule; mitigation is the Companion live traffic itself (every request/response round-trips through the real device) plus `atvproxy` captures if a decode error ever appears.

**L9 — tvOS 27 rejects Companion `_sessionStop` for the SID it issued.** Observed 2026-08-24 on the LAN Apple TV 4K (tvOS 27.0): `_sessionStart` returns a server-assigned SID, and the composite session id used for the rest of the session is `(server_sid << 32) | local_sid`, per the existing Companion port. On disconnect, sending `_sessionStop` back to the device for that same session answers with "Session not found" rather than a clean acknowledgement — the device does not recognize the composite id, or a bare SID, as one it owns. This is swallowed on disconnect exactly as pyatv does (pyatv does not treat a failed `_sessionStop` as fatal either), so it does not currently block teardown, but it means explicit session teardown is not verified to work end to end on this tvOS build. Mitigation: capture an iOS or tvOS sender's own `_sessionStop` exchange with a MITM proxy (`atvproxy`-style) to learn the current expected shape — id encoding, extra fields, or a different close handshake entirely — before relying on explicit session teardown for anything beyond best-effort cleanup.

**L11 — tvOS 27 sends HAP-framed blocks far larger than the 1024-byte cap.** Live: the first now-playing burst over the AirPlay data stream arrived as one 8931-byte plaintext block (valid Poly1305 tag). The 1024-byte limit therefore bounds only what this port sends; inbound frames are accepted up to the 16-bit length prefix. pyatv trusts the prefix the same way.

**L12 — pyatv's vendored `AudioRoute.proto` cannot decode tvOS 27's `ContentItemMetadata.type`.** The device sends a varint (the nested `AudioRouteType.Enum`), pyatv's file declares the wrapper message, and pyatv silently drops every affected `SET_STATE_MESSAGE` (`channels.py:220-225`), losing artist/album/shuffle/repeat. The Rust vendored copy is corrected (the only proto divergence, recorded in `crates/pyatv-proto-mrp/proto/README.md`). Worth an upstream report.

**L13 — MRP volume availability depends on playback and route state on tvOS 27.** An idle tunnel received no availability message and exposed no usable volume. During active grouped playback, the device reported absolute volume control, rejected relative control, and confirmed a change from 10% to 15%. Mitigation: treat availability messages as dynamic state and do not cache the idle result for the connection lifetime.

**L14 — The DMAP pairing responder's multicast receive path is unverified on a real link.** Review of Step 8 found the responder bound to the interface's unicast address, which on Linux silently excludes it from multicast delivery; fixed in 201bcb8 to bind the wildcard with `IP_MULTICAST_IF` and the group join per interface, and pinned by tests on the bind address. The development host has no multicast loopback, so end-to-end delivery of a `_touch-remote._tcp.local` browse query has not been observed. Also untested: coexistence with a resident avahi/mDNSResponder now relies on `SO_REUSEPORT` on both sockets. Verify with a legacy device or a second host running `dns-sd -B _touch-remote._tcp`.
