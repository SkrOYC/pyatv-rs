# Risk register

Distilled from the seven research reports. Each risk names its severity, why it is risky, and the concrete mitigation. "Interop" risks silently produce wrong bytes with no error until they hit a real device, so they dominate this list. Re-review at the start of each roadmap phase.

## High severity

**H1 — HAP SRP M1 uses unpadded `H(g)`; RustCrypto `srp` hardcodes the padded form.** `Client::process_reply()` cannot be used for HAP pairing. Mitigation: call the crate's public low-level primitives and `srp::utils::compute_m1_rfc5054(..., g_no_pad = true, ...)` directly (documented in `crypto-pairing.md` §9). Back it with a known-answer test from a captured pairing before trusting it. If the low-level API proves fragile, fall back to hand-rolling SRP math against `srp` 0.6.

**H2 — `srp` may still be a 0.7 release candidate.** An RC's API is not frozen. Mitigation: pin the exact validated version; track `RustCrypto/PAKEs` for the 0.7 stable release; keep 0.6 as a fallback; do not upgrade without re-running the SRP known-answer tests.

**H3 — Three distinct ChaCha20 nonce layouts and per-channel HKDF salt/info strings.** A single wrong byte decrypts garbage in one direction with no parse error. Mitigation: implement each nonce construction as an explicitly parameterized type (zero-prefix width + counter width); copy the salt/info table from `crypto-pairing.md` §3 verbatim; unit-test each channel's key derivation against captured fixtures. Note the AirPlay event channel swaps read/write info strings.

**H4 — OPACK and Companion have no public spec and no Rust prior art.** pyatv's `opack.py` and `atvproxy` are the only ground truth, and pyatv's own OPACK implementation is explicitly incomplete for some types (e.g. absolute-time 0x06). Mitigation: hand-write OPACK in its own crate with exhaustive round-trip property tests including open-ended containers and back-references; validate against `atvproxy` captures; treat pyatv as an incomplete spec for the flagged types and reverse-engineer them directly.

**H5 — MRP-over-AirPlay tunneling is actively evolving, even within pyatv.** Modern tvOS carries MRP inside an AirPlay 2 data-stream channel; any design frozen against a pyatv snapshot may be stale. Mitigation: abstract behind the `MrpTransport` trait so the message state machine is transport-independent; re-check pyatv `master` and capture against a live tvOS 26.x device at Step 4/5; verify the 2-second RTSP FEEDBACK heartbeat and data-channel sync/ack pattern (missing either tears down the tunnel after ~30 s).

## Medium severity

**M1 — Legacy AirPlay device-auth quirks must be replicated byte-for-byte.** The pair-setup IV last-byte `+1` increment, the doubled-SHA1 session key, the opaque trailing blob encrypted with the signature, and the Ed25519-seed-as-SRP-ephemeral reuse all diverge from textbook crypto and have no crate support. Mitigation: implement exactly as `crypto-pairing.md` §2.2/§5.4/§6 describes; do not "fix" the oddities; validate with a legacy-device capture. Lower severity than H-items because legacy AirPlay is old and may be deprioritized.

**M2 — prost compiles pyatv's proto2 corpus perfectly and then silently drops every `extend` block.** Resolved by a measured spike (`docs/research/mrp-protobuf-spike.md`, 2026-08-24) and closed in code. The compile half was never in doubt: prost-build 0.14.4 built all 77 vendored files with no errors, and protox 0.9.1 produced **byte-identical** output to protoc 35.1, so the toolchain is pure Rust and the crate builds offline with no `$PROTOC`. The real finding is the second half — prost has no concept of proto2 extensions at all (the word appears once in prost-build's source, in an unrelated doc comment) and its decoder discards unknown fields, so a decoded `ProtocolMessage` loses the payload with no error. Since every MRP message *is* an extension, that would have produced a client that reads `type` and nothing else. Mitigation, implemented: `build.rs` walks the same `FileDescriptorSet` a second time and generates a typed handle per extension, and `src/protobuf/{wire,extensions}.rs` reads and splices the field directly on the serialised envelope, in ascending tag order so output stays byte-identical to the reference implementation. Eight known-answer vectors generated by pyatv's own protobuf runtime round-trip byte for byte. rust-protobuf 3.7.2 was spiked as the documented fallback and does support extensions natively; it was rejected on API and lint grounds, not capability — see the spike §5 if the decision ever needs revisiting. Two facts worth carrying forward: `mrp-companion.md` §1.3's claim that the extension field number equals the `Type` enum value is wrong for all 55 messages, and the `protobuf` 4.x line on crates.io is Google's separate project, not a rust-protobuf upgrade.

**M3 — AES-CTR and `NSKeyedArchiver` plist semantics are unverified against real captures.** `ctr::Ctr128BE<Aes128>` full-16-byte-IV-as-counter semantics and whether the `plist` crate handles keyed-archiver payloads (Companion keyboard `_tiD`) are assumptions. pyatv wrote its own `keyed_archiver.py`, hinting a custom Rust impl may be needed. Mitigation: byte-exact known-answer tests before depending on either; be prepared to hand-write a small keyed-archiver reader.

**M4 — Custom AirPlay HTTP/RTSP codec is unavoidable and easy to get subtly wrong.** Reverse connections, single-socket dual roles, an event channel. Mitigation: sans-io `tokio_util::codec` with `Content-Length` buffering (`Ok(None)` on partial frames), round-trip tests, and capture-based tests; do not attempt to force reqwest/hyper.

**M5 — Dependency currency and the fast-moving dalek/RustCrypto stack.** `ed25519-dalek`/`x25519-dalek` bumped to 3.0.0 in a recent wave; the crypto set must co-resolve on one RustCrypto trait generation. Mitigation: the Step 0 scaffold validates co-resolution; re-verify versions and read full rustdoc at each phase; `cargo-deny` advisories + `cargo-machete` in CI; `cargo update` guarded by resolver v3 MSRV-awareness.

## Low severity / watch

**L1 — pyatv itself is not fully correct against the newest tvOS.** Open upstream issues on `play_url`, RTSP heartbeat desync, and discovery flakiness, plus reduced maintainer bandwidth. Mitigation: treat pyatv as spec-of-record but validate independently against a real device; do not inherit unverified paths (pyatv has `# TODO` unverified-signature comments in its pairing flows — decide deliberately whether to be stricter).

**L2 — `~/.pyatv.conf` on-disk compatibility is not free.** Reverse-engineering pyatv's `StorageModel`/`Settings` field names is required if credential-file migration is a goal. Mitigation: treat it as an explicit, separately-scoped decision (see `ARCHITECTURE.md` §8); the credential *string* format is replicated regardless.

**L3 — RAOP may or may not require ALAC encoding.** pyatv's SDP template suggests raw PCM (L16); the `alac-encoder` crate is stale. Mitigation: confirm with a live capture at Step 6 before pulling in an ALAC encoder.

**L4 — Provisional MSRV (1.88).** Chosen for let-chains; a dependency may demand higher. **Verified 2026-08-25 and still holding:** `cargo check --workspace --all-features --locked` compiles clean on rustc 1.88.0 with the current lockfile, so no bump is needed. Mitigation: the `msrv` job in `.github/workflows/ci.yml` reads the floor out of `[workspace.package] rust-version` and builds against exactly that toolchain on every PR — it does not repeat the number, so the job and the manifest cannot drift. Note that `cargo msrv verify` is *not* what runs there: cargo-msrv 0.19.3 looks for `package.rust-version` and cannot see `[workspace.package] rust-version` in a virtual manifest, so it fails at the workspace root before checking anything. It does work per member (`cargo msrv find --path crates/<name>`) and is in the devenv for exactly that job — finding a *new* floor after a dependency bump. Bump deliberately with a version note (an MSRV bump is a minor-version change for a library).

**L5 — Point-in-time research.** All crate versions, star counts, and pyatv behavior were captured 2026-08-24. Mitigation: re-verify at the start of each phase; the reports cite their sources for exactly this reason.

**L6 — Do not implement FairPlay.** No open implementation exists; it depends on Apple hardware key material; pyatv only parses its advertisement. Mitigation: explicitly out of scope. Revisit only if a future feature genuinely requires classic encrypted RAOP, which would be net-new research with no precedent.

**L6 — Upstream discovery quirks are preserved deliberately, not fixed.** The Step 1 port keeps pyatv's observed behaviour where it looks like a bug, so that a real device sees the same traffic and the same config comes out: `create_service_queries` chunks questions with a 4-wide window on a 3-stride (duplicating boundary questions), `BaseService.merge` never updates port/identifier/pairing, Companion's `PAIRING_*_MASK` constants disagree with their own derivation comments, `DeviceInfo.operating_system` and `lookup_os` disagree on Gen2/Gen3, and the `"22J354": "17.0"` version-table entry is almost certainly a typo. Each is pinned by a test with a comment citing `docs/research/discovery-port-spec.md` §9. Mitigation: decide per item, with a device capture in hand, whether to keep or diverge — never silently.

**L7 — Multicast discovery is IPv4-only and interface enumeration is host-specific.** pyatv's multicast client joins `224.0.0.251` on every IPv4 interface via `netifaces`; the port uses `if-addrs` + `socket2`, which is enough on Linux/macOS but untested on Windows and skips IPv6 entirely, as pyatv does. Mitigation: the unicast path (`--scan-hosts`) is the fallback on any network where multicast misbehaves; revisit IPv6 only if a device is seen advertising AAAA-only.

**M6 — Stricter-than-pyatv pairing verification may reject a device pyatv accepts.** pyatv never checks the accessory's SRP proof (its `step2` compares a value with itself), never verifies the M6 / pair-verify M2 Ed25519 signatures, and never inspects the final state/error TLV (`docs/research/hap-pairing-port-spec.md` §8). The Rust port verifies all three, per the HAP specification, because a silent skip hides both wrong-PIN and man-in-the-middle failures. If a real device ever fails one of these checks where pyatv would proceed, treat it as a finding to capture with `atvproxy` — do not loosen the check blindly; add a documented per-check lenient option only against evidence.

**L8 — `srp` is a release candidate (0.7.0-rc.3) whose `g_no_pad` documentation is backwards.** Verified by a compiled probe (`docs/research/crate-verification-2026-08-24.md`): HAP needs `g_no_pad = true`, and `process_reply()` cannot be used because it hardcodes padded `g`. The port calls `srp::utils::compute_m1_rfc5054` directly and pins the behaviour with client↔server tests plus a fixed-seed KAT, so an rc→final API change will fail the build or the tests, never silently change the proof.

**M7 — AirPlay HAP pairing on this tvOS 27 device never displays a PIN (Companion does) — but the tunnel does not need it.** Observed 2026-08-24 against an Apple TV 4K gen 3 (`flags=0x18644`: HomeKit-pairing bit 0x200 set, PIN-required bit 0x8 clear): `/pair-pin-start` and pair-setup M1 both return 200 and M2 arrives, but no code appears on screen or in Settings → AirPlay and HomeKit. Our request bytes equal pyatv's, and pyatv's own troubleshooting page documents the same symptom, so this is device behaviour rather than a port defect. **Resolved as a blocker on 2026-08-24 by a live experiment** (`docs/research/airplay-tunnel-auth-experiment-2026-08-24.md`, reproducible via `crates/pyatv-proto-airplay/examples/airplay_verify_probe.rs`): the AirPlay endpoint accepts HAP pair-verify against the credentials from **any** completed HAP pairing on the device, including the Companion one. M1–M4 complete with `200`/`200`, the accessory's identifier and Ed25519 signature verify against the Companion-stored `atv_id`/`ltpk`, the `Control-*` transport keys work first try, and both `GET /info` and the `isRemoteControlOnly` `SETUP` succeed over the encrypted channel — confirmed twice, with this port's credentials and with pyatv's own. Transient pairing is *not* an alternative here: `POST /pair-setup` with `X-Apple-HKP: 4` is refused `470 Connection Authorization Required` with an empty body, and a control run proved the refusal is about the transient branch rather than about the withheld `/pair-pin-start`. Mitigation, now concrete: Companion pairing (Step 3) remains the only pairing path on modern tvOS, and the facade must fall back to the Companion service's HAP credentials when the AirPlay service has none of its own — a deliberate divergence from pyatv's `extract_credentials`, which only ever reads the AirPlay service's own `credentials`. Keep the AirPlay pair-setup path (it is hermetically tested end to end) for older devices, and revisit with an `atvproxy` capture of an iOS sender if AirPlay-only devices (HomePod, where only transient credentials are accepted) need it. Residual risk: whether tvOS ever expires a pairing used from a protocol other than the one that created it, which would surface as a sudden `470` on a previously working pair-verify.

**L10 — tvOS 27 answers the remote-control `SETUP` with `skipRecord: true`, a key pyatv does not know about.** Observed 2026-08-24 (`docs/research/airplay-tunnel-auth-experiment-2026-08-24.md` experiment 4): the event-channel `SETUP` reply is exactly `{eventPort: <fresh per SETUP>, skipRecord: true}`, with no `timingPort`. `skipRecord` appears nowhere in pyatv, and the only thing there is to skip at that point is the `RECORD` pyatv sends unconditionally between the event and data `SETUP`s (`ap2_session.py:75-82`) — so a byte-faithful port sends a request the receiver has just said it does not want. This is a live candidate explanation for the tvOS-era tunnel flakiness in L1/H5. Mitigation: honour `skipRecord` when the receiver sets it, and test both branches against the device once the data channel exists; capture an iOS sender with `atvproxy` to confirm what Apple's own controller does. Also do not assume `timingPort` is present in a `SETUP` reply.

**M8 — pyatv's OPACK encoder and decoder disagree on back-reference interning.** Found by a property test during the port: pyatv interns by encoded length on the pack side (`opack.py:129`) and by type on the unpack side (`opack.py:208-238`), so `pack([[1, 2], "a", "a"])` produces bytes pyatv's own `unpack` rejects. The Rust codec uses the decoder's rule on both sides — the side exercised against real devices — and reproduces every pyatv test vector byte for byte. Residual risk: a payload where Apple's decoder follows a third rule; mitigation is the Companion live traffic itself (every request/response round-trips through the real device) plus `atvproxy` captures if a decode error ever appears.

**L9 — tvOS 27 rejects Companion `_sessionStop` for the SID it issued.** Observed 2026-08-24 on the LAN Apple TV 4K (tvOS 27.0): `_sessionStart` returns a server-assigned SID, and the composite session id used for the rest of the session is `(server_sid << 32) | local_sid`, per the existing Companion port. On disconnect, sending `_sessionStop` back to the device for that same session answers with "Session not found" rather than a clean acknowledgement — the device does not recognize the composite id, or a bare SID, as one it owns. This is swallowed on disconnect exactly as pyatv does (pyatv does not treat a failed `_sessionStop` as fatal either), so it does not currently block teardown, but it means explicit session teardown is not verified to work end to end on this tvOS build. Mitigation: capture an iOS or tvOS sender's own `_sessionStop` exchange with a MITM proxy (`atvproxy`-style) to learn the current expected shape — id encoding, extra fields, or a different close handshake entirely — before relying on explicit session teardown for anything beyond best-effort cleanup.

**L11 — tvOS 27 sends HAP-framed blocks far larger than the 1024-byte cap.** Live: the first now-playing burst over the AirPlay data stream arrived as one 8931-byte plaintext block (valid Poly1305 tag). The 1024-byte limit therefore bounds only what this port sends; inbound frames are accepted up to the 16-bit length prefix. pyatv trusts the prefix the same way.

**L12 — pyatv's vendored `AudioRoute.proto` cannot decode tvOS 27's `ContentItemMetadata.type`.** The device sends a varint (the nested `AudioRouteType.Enum`), pyatv's file declares the wrapper message, and pyatv silently drops every affected `SET_STATE_MESSAGE` (`channels.py:220-225`), losing artist/album/shuffle/repeat. The Rust vendored copy is corrected (the only proto divergence, recorded in `crates/pyatv-proto-mrp/proto/README.md`). Worth an upstream report.

**L13 — Volume is unavailable over the MRP tunnel on tvOS 27.** No `VOLUME_CONTROL_AVAILABILITY_MESSAGE` arrives after bring-up, so `Volume`/`SetVolume`/`VolumeUp`/`VolumeDown` report Unavailable, and Companion registers no Audio interface. Unknown whether a subscription is missing or tvOS changed; needs an `atvproxy`-style capture of an iOS sender.
