# Prior art for a pure-Rust pyatv reimplementation

Research date: 2026-08-24. All version numbers, star counts, and dates below were pulled live from the crates.io API (`https://crates.io/api/v1/crates/<name>`) and the GitHub REST API (`https://api.github.com/repos/<owner>/<repo>`) on this date unless noted otherwise — do not trust a WebFetch prose summary over the raw JSON if the two disagree (one was caught inventing a "494K lines of code" figure for a crate that the API showed has 14,967 lines; the JSON was used instead).

## How to read this report

Every project below gets: URL, language, license (with an explicit copyleft/permissive call-out), scope, activity signal (stars, last push date, archived flag), and concrete lessons. The report closes with a licensing decision table and a gap analysis for the parts of pyatv's protocol surface that no Rust project has attempted yet.

## License legend used throughout

- PERMISSIVE = MIT, Apache-2.0, BSD, or dual MIT/Apache-2.0 — safe to read *and* to port code from (with attribution) into a permissively-licensed Rust project.
- WEAK-COPYLEFT = LGPL — safe to read; linking (especially Rust's default static linking) creates real distribution obligations, treat as "read for behavior, do not vendor code, avoid depending on it if the end product must stay permissive."
- STRONG-COPYLEFT = GPL-2.0/GPL-3.0 — safe to read as documentation-of-behavior only. Do not copy, transliterate, or "clean-room-adjacent" port any code from these. Treat like reading a spec, not a source tree.
- UNCLEAR/NOASSERTION = GitHub's license detector could not classify it, or the repo mixes licenses per-file (shairport-sync is exactly this case) — verify file-by-file before touching, and default to treating it as unsafe to copy from.

## 1. pyatv itself (the thing we are reimplementing)

- URL: https://github.com/postlund/pyatv, docs at https://pyatv.dev, package at https://pypi.org/project/pyatv
- Language: Python (asyncio). License: MIT (PERMISSIVE — confirmed via GitHub API `license.spdx_id: "MIT"`).
- Activity: 1,167 stars, pushed 2026-08-14 (10 days before this report), 252 open issues — actively maintained, lead maintainer Pierre Ståhl.
- Scope: unified facade over four protocols — DMAP (legacy iTunes/AirTunes remote, port 3689 HTTP server with binary TLV encoding), MRP (Media Remote Protocol, Protobuf-over-TCP, mDNS type `_mediaremotetv._tcp.local`), Companion Link (OPACK-over-TLS/ChaCha20, mDNS type `_companion-link._tcp`), and AirPlay/RAOP (audio+video streaming, HAP-based pairing). See https://pyatv.dev/documentation/protocols/ and https://github.com/postlund/pyatv/blob/master/docs/documentation/protocols.md for the maintained protocol matrix (remote control → MRP + Companion; metadata/now-playing → DMAP + MRP + AirPlay2; audio → RAOP; video/mirroring → AirPlay).
- Because pyatv is MIT, its Python source is legally safe to read line-by-line as a protocol reference and even to port algorithmically (with attribution) — this is the single most valuable prior-art asset for this project, more so than any GPL C project, precisely because of the license. Treat `pyatv/protocols/` in the pyatv tree as the primary spec-of-record when the OpenAirplay doc and this report disagree.
- pyatv ships `atvproxy`, a MITM proxy tool for reverse-engineering the Companion protocol by decrypting and logging real device traffic (https://pyatv.dev/documentation/atvproxy/) — reuse this tool during development instead of re-deriving OPACK/Companion framing from scratch.
- Companion issue #655 (https://github.com/postlund/pyatv/issues/655) is pyatv's own historical reverse-engineering thread for the Companion protocol and is worth mining for edge cases.

## 2. HomeKit Accessory Protocol (HAP) in Rust — the closest existing "sibling" protocol

AirPlay 2's pairing (pair-setup/pair-verify) and Companion's pairing both reuse HAP's HomeKit-based Pairing (HKP) design, so Rust HAP implementations are directly relevant prior art for our crypto/pairing layer, not just an analogy.

### hap-rs (ewilken/hap-rs)
- URL: https://github.com/ewilken/hap-rs, crate `hap` on crates.io (https://crates.io/crates/hap).
- License: dual MIT/Apache-2.0 (PERMISSIVE, confirmed via GitHub API).
- Activity: 217 stars, last push 2024-08-05 — over two years stale relative to 2026-08-24; crates.io `max_stable_version` is `0.0.10`, and the newest published version is a pre-release `0.1.0-pre.15` from 2022-08-12, with only 315 recent (90-day) downloads out of 37,719 lifetime. Treat as effectively unmaintained/reference-only, not a dependency to build on.
- Scope: full HAP-over-IP accessory server (not controller) — HTTP server exposed via mDNS (`libmdns` 0.6), SRP-6a pairing, ChaCha20-Poly1305 session encryption, Ed25519/X25519 identity keys, TLV8 codec, HAP characteristic/service model with codegen for Apple's published characteristic database. No BLE transport.
- Dependency snapshot from `Cargo.toml` (https://github.com/ewilken/hap-rs/blob/main/Cargo.toml): `srp` 0.5, `ed25519-dalek` 1.0, `x25519-dalek` 0.6, `chacha20poly1305` 0.8, `hkdf` 0.11, `sha2` 0.9, `aead` 0.4, `hyper` 0.14, `tokio` 1.8, `libmdns` 0.6. All of these are now multiple major versions behind current crates.io releases (e.g. `srp` is at 0.6.0 stable / 0.7.0-rc.3 today, `ed25519-dalek` has moved well past 1.0) — do not copy these pinned versions, only the *shape* of the dependency graph (SRP + X25519 + Ed25519 + ChaCha20-Poly1305 + HKDF-SHA is the right crypto stack for HAP-family pairing).
- Lesson: because it's MIT/Apache-2.0, the SRP-6a session flow, TLV8 codec, and mDNS TXT-record layout in this crate can be read and adapted directly. Its staleness is itself a lesson: a HAP-shaped crate needs active maintenance because Apple's characteristic/service catalog and TLS/crypto crate churn both move fast; budget for keeping pairing crypto deps current.

### hap-controller (phunapps/hap-rust)
- Crate: https://crates.io/crates/hap-controller, repo https://github.com/phunapps/hap-rust.
- License: Apache-2.0 (PERMISSIVE, confirmed via GitHub API), not a fork of ewilken/hap-rs (GitHub API `parent` field is null) — an independent implementation.
- Activity: very recent — crates.io last publish 2026-08-07 (17 days before this report), version 3.1.0, but low adoption (672 downloads total, all in the current window) and 0 GitHub stars — a new/small project, worth watching but not yet proven.
- Scope: HAP *controller* (not accessory) role — discover, pair, connect, read/write/subscribe characteristics. This is the complementary half of what hap-rs does (hap-rs plays accessory; hap-controller plays iOS-app-equivalent controller), and pairing-as-a-controller is architecturally closer to what an Apple TV *client* library needs than an accessory-server crate is.
- Because it's actively published in 2026 against modern Rust editions, this is worth periodic re-checking as it matures — it is the only actively-maintained Rust HAP crate found in this survey.

### Other HAP-adjacent Rust crates found but not deeply investigated
- `hap` and `hap-controller` are the two live crates; a search also surfaced `MihaelBercic/HomeKit-Accessory-Protocol` (small, unverified maintenance) — low priority, not independently verified here.

### shairplay-rust deep dive (most relevant single Rust prior-art project)

- crates.io identity: crate name `shairplay`, published by `metaneutrons` (Fabian Schmieder), current version 0.7.0 (published 2026-07-03), `rust_version = "1.88"`, `edition = "2024"`. Homepage field points to https://github.com/metaneutrons/shairplay-rust; note the crates.io `repository` metadata field is stale/incorrect (it still points at an old `fabianlindfors/shairplay` URL that 404s) — always resolve via the `homepage` field for this crate, not `repository`.
- Real size per crates.io linecount metadata: 14,967 lines of Rust across 49 files (**not** the "494K lines" a WebFetch summarization pass initially reported — that number was a model hallucination and is flagged here as a cautionary example of why raw API JSON must be checked**).
- License: LGPL-3.0-or-later. GitHub confirms same (`license.spdx_id: "LGPL-3.0"`). This is a real decision point (see §6 below) if our project intends to stay permissively licensed.
- Claims to be AP1+AP2 receiver, clean-room (`#![forbid(unsafe_code)]`), with a feature-flagged Cargo.toml: `ap2` feature pulls in `chacha20poly1305`, `hkdf`, `num-bigint`, `uuid`, `symphonia`; `resample` pulls `rubato`; `video`/`hls` build on `ap2`. Architecture per its README: `raop/` (RTSP+RTP server), `crypto/` (RSA, Ed25519, AES, FairPlay, HomeKit pairing), `codec/` (ALAC/AAC + resampling via symphonia/rubato), `proto/` (SDP, HTTP/RTSP, binary plist, HTTP Digest auth), `net/` (TCP, mDNS via `astro-dnssd` on macOS and `mdns-sd` on Linux), `dacp/` (AP1 remote control client).
- Its own acknowledgments section cites: the original C `shairplay` project, `shairport-sync`, `pair_ap` (cited specifically for SRP-6a/TLV test vectors), Emanuele Cozzi's "AirPlay 2 Internals" writeup (https://emanuelecozzi.net/docs/airplay2), the openairplay-spec, pyatv (for Companion-link research), and "rairplay" (the GPL-3.0 project above) — i.e., it triangulates from the same sources this report recommends, which is a useful sanity check that our source list is the right one.
- Adoption is still small (2,344 lifetime downloads, 1,603 in the most recent window as of 2026-08-24; only 13 GitHub stars) — promising architecture and feature-flag design worth studying, but not yet a crate we would casually depend on in production; the LGPL license is the bigger blocker regardless of maturity.

### FairPlay authentication warning

Several of the above (shairplay-rust's `crypto/` module, the original C `shairplay`, UxPlay) implement or stub "FairPlay" authentication — Apple's legacy AirPlay 1 DRM/auth handshake that was originally cracked via leaked/reverse-engineered keys (notably the "FairPlay" auth keys extracted from AirPort Express firmware years ago, the same lineage used by the original `shairplay` C library). This is legally and technically the highest-risk single piece of protocol surface in the whole AirPlay stack: it is not officially documented anywhere, all known implementations trace back to the same leaked key material, and Apple has periodically revoked/rotated things that depend on it. Modern AirPlay 2 pairing (HAP-based SRP-6a + Ed25519, described above) supersedes FairPlay for current-generation devices and is the path this project should prioritize; FairPlay-based AP1 auth should be treated as legacy-compat, lowest priority, and implemented only if a concrete device/use-case requires it.

## 4. AirPlay senders/receivers in other languages (protocol truth, not code)

These are not Rust, but are the highest-fidelity behavioral references available — read them as documentation of wire behavior, never as a source to port from if the license is GPL.

### shairport-sync (mikebrady/shairport-sync)
- URL: https://github.com/mikebrady/shairport-sync. Language: C.
- License: GitHub API reports `NOASSERTION` — this project mixes licenses per subsystem historically (core is BSD/Apache-ish, some vendored code differs); do not assume the whole tree is permissive. **Verify the specific file's header before treating any snippet as reusable; default to treat-as-GPL-equivalent (i.e., read-only) for anything not explicitly marked otherwise.**
- Activity: 8,824 stars, pushed 2026-08-24 (today — actively maintained), 18 open issues. This is the most mature, most-referenced open-source AirPlay *receiver* in any language.
- Scope: AirPlay 1 + AirPlay 2 audio receiver for Linux/FreeBSD/OpenBSD. Notable architectural pattern worth copying (as *design*, not code): AirPlay 2's precision timing requirement (PTP, IEEE 1588) is handled by a **separate companion daemon, NQPTP**, rather than embedding a PTP stack in the audio player process — this process-separation pattern is a strong candidate for our own architecture (a dedicated timing/clock-sync task or even process, decoupled from RTSP/RTP handling). Also documents AAC/ALAC decode paths, metadata delivery via named pipe/UDP, and multiple audio backend targets (ALSA, PipeWire, PulseAudio, sndio). See its `AIRPLAY2.md` (https://github.com/mikebrady/shairport-sync/blob/master/AIRPLAY2.md) for the maintainer's own protocol notes — this is a primary source, written by someone who reverse-engineered AirPlay 2 independently and documented it.

### OwnTone / forked-daapd (owntone/owntone-server)
- URL: https://github.com/owntone/owntone-server (formerly `forked-daapd`, itself a fork of `mt-daapd`/Firefly Media Server). Language: C.
- License: GPL-2.0 (STRONG-COPYLEFT, confirmed via GitHub API). Do not copy code; read `src/outputs/raop.c` as a behavioral reference only.
- Activity: 2,542 stars, pushed 2026-08-21 (3 days before this report) — actively maintained, mature (7,457+ commits).
- Scope: full DAAP media server that *sends* (not receives) to AirPlay 1+2, Chromecast, and Roku targets, plus DACP-based Apple Remote support. This is the single most complete open-source AirPlay **sender** implementation available (most other projects, including pyatv itself, focus on receiving/control rather than being a full streaming source), making `raop.c` valuable for understanding sender-side RTSP/RTP session setup, retransmission handling, and multi-target sync — but only as documentation, given the GPL-2.0 license.

### UxPlay (FDH2/UxPlay, canonical fork — note: also mirrored under antimof/UxPlay historically)
- URL: https://github.com/FDH2/UxPlay. Language: C/C++ with GStreamer.
- License: GPL-3.0 (STRONG-COPYLEFT, confirmed via GitHub API). Inherits from the original LGPLv2.1+ `shairplay` C library in `lib/`, but the UxPlay wrapper itself is GPL-3.0 — treat the whole combined work as GPL for our purposes.
- Activity: 2,986 stars, pushed 2026-08-22 (2 days before this report) — very actively maintained, version 1.74 as of its README.
- Scope: AirPlay-Mirror (AAC audio + H.264/H.265 screen mirroring) and AirPlay-Audio (lossless ALAC) receiver, plus experimental YouTube-HLS video support. Explicitly documents that it implements only the "Legacy Protocol" for AirPlay2 — i.e., even one of the most popular open-source AirPlay2 receivers has *not* achieved full modern AirPlay2 parity, which is a useful calibration point for how hard this protocol surface is.
- Architecture lesson: heavy reliance on GStreamer for A/V pipeline plumbing (hardware-accelerated decode via VA-API/CUDA/V4L2) — not directly portable to a Rust decision, but confirms that screen-mirroring video decode is treated as "delegate to a mature multimedia framework" even by mature C projects, rather than hand-rolled. A Rust equivalent should likewise plan to delegate H.264/H.265 decode to an existing crate (e.g. an FFI binding or a pure-Rust decoder) rather than writing a decoder from scratch.

### openairplay/airplay2-receiver
- URL: https://github.com/openairplay/airplay2-receiver. Language: Python.
- License: GitHub API reports `license: null` (no machine-detected license) — treat as all-rights-reserved/ask-first for code; the project's own framing (per its README, echoed across multiple sources) is explicitly "for educational/research purposes" using "freely available information," which supports reading it as a reverse-engineering reference but not as a code source.
- Activity: 2,382 stars, pushed 2026-06-29 — the widely-cited reference implementation that both `shairplay-rust` and much of the broader AirPlay2 reverse-engineering community (including the openairplay-spec itself) built on. Treat as a primary behavioral reference on par with shairport-sync's AIRPLAY2.md.

### node-appletv-x / node-appletv (MRP reference implementations)
- URLs: https://github.com/stickpin/node-appletv-x (MIT, **archived**, last push 2020-09-17) and https://github.com/evandcoleman/node-appletv (original, same protocol scope). Language: TypeScript/Node.
- License: MIT (PERMISSIVE) on node-appletv-x — safe to read and adapt.
- Scope: pure MRP (Media Remote Protocol) client for 4th-gen+ Apple TV — SRP-based pairing, then length-prefixed Protobuf frames over TCP, encrypted post-pairing. Both projects are stale/archived (pre-2021), reflecting that most of the community's energy has since shifted to Companion Link as Apple has de-emphasized MRP for control (though MRP remains relevant for now-playing/metadata per pyatv's own protocol matrix).
- The author of node-appletv also wrote a widely-cited explainer, "Apple TV, Meet My Lights: Dissecting the Media Remote Protocol" (https://medium.com/@evancoleman/apple-tv-meet-my-lights-dissecting-the-media-remote-protocol-d07d1909ad82) — useful narrative walkthrough of MRP's SRP pairing → length-prefixed Protobuf → post-pairing encryption flow, though this report could not fetch its full text directly (403 on automated fetch); read it manually.
- `jeanregisser/mediaremotetv-protocol` (https://github.com/jeanregisser/mediaremotetv-protocol) is a dedicated, unofficial MRP **specification** repo (152 stars, no explicit license detected, last pushed 2018-02-27 — old but still the most-cited standalone MRP spec) containing `.proto` message definitions; useful as a starting point for generating Rust Protobuf bindings via `prost`, but cross-check every message against current pyatv source since MRP has surely drifted since 2018.

### node-appletv-remote (newer, multi-protocol)
- Surfaced via search as "a pure Node.js library and CLI for remote controlling Apple TV devices... using AirPlay 2, MRP, and the Companion Link protocol" — i.e., a more modern, broader-scope analog to pyatv in the Node ecosystem. Not independently deep-dived in this pass (no GitHub API metadata pulled); worth a follow-up look given it apparently spans all three control protocols pyatv supports.

## 5. mDNS / service-discovery crates in Rust (real-world usage signal)

This is the one layer of the stack where Rust prior art is unambiguously mature and safe to depend on directly.

- **mdns-sd** — https://github.com/keepsimple1/mdns-sd, crate https://crates.io/crates/mdns-sd. License Apache-2.0 (PERMISSIVE, confirmed). This is the clear market leader: 220 GitHub stars, pushed 2026-08-21 (3 days before this report), and on crates.io: 4,410,829 lifetime downloads, 1,821,871 in the most recent window, current version 0.21.0 (published 2026-08-12). Explicitly "no async runtime dependency" with an optional `async` feature (built on `flume`), plus `serde` and `logging` feature flags. `shairplay-rust` itself depends on this crate for Linux mDNS. **Recommendation: use `mdns-sd` as the primary discovery crate** for `_raop._tcp`, `_airplay._tcp`, `_mediaremotetv._tcp`, and `_companion-link._tcp` service browsing/advertisement — it is by a wide margin the most battle-tested pure-Rust option found.
- **zeroconf** (https://crates.io/crates/zeroconf) — cross-platform *wrapper* around native Bonjour (macOS/Windows) or Avahi (Linux) via FFI, not a pure-Rust reimplementation. Has a companion `zeroconf-tokio` crate for async use. Worth considering only if native OS mDNS daemon integration (e.g. coexisting cleanly with a running `mDNSResponder`/Avahi on the host) is a hard requirement; otherwise `mdns-sd` avoids the FFI/native-daemon dependency entirely.
- **simple-mdns**, **astro-dnssd**, **bonjour-sys**, **avahi-sys** — lower-traffic or lower-level alternatives found in the same search; `astro-dnssd` (a safe wrapper over macOS's native `dns_sd` API) is notably what `shairplay-rust` uses specifically *on macOS* while falling back to `mdns-sd` elsewhere, suggesting a possible pattern of "pure-Rust mdns-sd everywhere, with an optional native-macOS path" if Bonjour-daemon-cooperation on macOS ever becomes a requirement — not recommended as a default, only as a documented escape hatch.

## 6. Codec crates (ALAC)

- **symphonia** / **symphonia-codec-alac** — https://github.com/pdeljanov/Symphonia, crate https://crates.io/crates/symphonia-codec-alac. Pure-Rust multi-format demux/decode library including an ALAC decoder; the crate's own docs recommend depending on the umbrella `symphonia` crate with the `alac` feature rather than the codec crate directly. `shairplay-rust` depends on `symphonia` for its AAC path per its Cargo.toml feature list. This is the clear default choice for ALAC (and AAC, if needed for AP2) decode in Rust — verify current version and exact feature-flag name on crates.io/docs.rs before pinning, this report did not pull its precise version number.
- **alac-encoder** (https://github.com/LinusU/rust-alac-encoder, crate `alac-encoder`) — a Rust port of Apple's own open-source ALAC encoder; relevant if the project ever needs to *encode* ALAC (e.g. building a sender/transmitter role, not just a receiver/controller), which is plausible given pyatv's own RAOP-sending capability for AirPlay speaker output.

## 7. SRP-6a building block (shared across HAP, AirPlay 2, and Companion pairing)

- **srp** (RustCrypto/PAKEs) — https://github.com/RustCrypto/PAKEs, crate https://crates.io/crates/srp. License Apache-2.0/MIT dual (RustCrypto's standard, PERMISSIVE — not independently re-verified per-crate here but consistent with all RustCrypto crates). Pure-Rust RFC 5054 SRP-6a built on `crypto-bigint` with constant-time arithmetic. Current stable `0.6.0`, with `0.7.0-rc.3` in pre-release, 102,201 lifetime downloads / 37,862 recent — solidly adopted within the Rust crypto ecosystem generally (RustCrypto crates are the closest thing Rust has to an official crypto-primitives project). hap-rs depends on an older `srp` 0.5.
- HomeKit-family pairing (which AirPlay 2's pair-setup/pair-verify and Companion Link both reuse) specifically uses the **3072-bit SRP group from RFC 5054 with SHA-512**, confirmed across multiple sources (Apple's own HomeKit Accessory Protocol Specification, and community documentation). The `srp` crate supports configurable group parameters — confirm the 3072-bit group constant is available/selectable before committing to it as the pairing dependency.
- Concrete HKDF salt/info string constants recovered from the openairplay-spec's HKP page (https://openairplay.github.io/airplay-spec/pairing/hkp.html) for the post-pair-verify control channel: HKDF-SHA-512 with Salt `"Control-Salt"`, Info `"Control-Write-Encryption-Key"` (client→accessory) / `"Control-Read-Encryption-Key"` (accessory→client), 32-byte output, ChaCha20-Poly1305 framing as `N:n_bytes:tag` with a 64-bit counter inside a 96-bit nonce structure. For the optional legacy MFi-signed pair-setup path: Salt `"Pair-Setup-Encrypt-Salt"` / Info `"Pair-Setup-Encrypt-Info"` / Nonce `"PS-Msg04"` for the M4 encrypted-data blob, and a separate HKDF derivation with Salt `"MFi-Pair-Setup-Salt"` / Info `"MFi-Pair-Setup-Info"` feeding an RSA-1024/SHA-1 MFi signature — this legacy MFi path is low priority (see FairPlay warning above; MFi auth requires a licensed Apple MFi authentication coprocessor/keys in the general case and should not be a near-term goal). Cross-check every one of these strings against the live spec pages and pyatv source before implementing; this report's WebFetch-based extraction of the openairplay-spec HKP page was incomplete (it could not retrieve the full M1–M6 message table in one pass) and should be re-fetched section-by-section during implementation, not treated as complete.
- HAP/HomeKit message numbering pattern to reuse conceptually: pair-setup is M1 (SRP Start Request) → M2 (SRP Start Response) → M3 (SRP Verify Request) → M4 → M5 → M6 (Exchange Response); pair-verify follows an analogous shorter M1–M4 exchange using Ed25519/X25519. Confirm exact TLV8 tag numbers and message contents against Apple's own HomeKit Accessory Protocol Specification (non-commercial release is circulated as a PDF, e.g. one mirror at https://forum.iobroker.net/assets/uploads/files/1634848447889-apple-spezifikation-homekit.pdf — verify this is still the current non-commercial spec revision before relying on it) rather than this summary alone.

## 8. Gap analysis — what has never been done in Rust

Based on this survey, the following pieces of pyatv's surface area have **no known Rust implementation at all**, serious or otherwise, as of 2026-08-24:

1. **MRP (Media Remote Protocol) in Rust.** Every MRP implementation found (node-appletv, node-appletv-x, mediaremotetv-protocol spec repo) is JavaScript/TypeScript or a bare `.proto` spec; the Rust AirPlay ecosystem surveyed here is entirely focused on RAOP/AirPlay streaming and HAP-style pairing, not on MRP's Protobuf-over-TCP remote-control channel. This is a clean-slate task: define `.proto` messages (starting from `jeanregisser/mediaremotetv-protocol`, cross-checked against current pyatv source since that spec repo is stale since 2018), generate bindings with `prost`, and layer SRP pairing + post-pairing encryption on top using the same crypto stack as HAP (the `srp` + `ed25519-dalek`/`x25519-dalek` + `chacha20poly1305` + `hkdf` combination validated across multiple projects above).
2. **Companion Link / OPACK in Rust.** No Rust implementation was found anywhere in this survey. The only implementations located at all were Swift (a macOS app called "itsytv" doing ground-up OPACK decoding) and the reference Python in pyatv itself. OPACK is Apple's proprietary internal serialization format (from the private CoreUtils framework) with no public specification; pyatv's own Companion code and its `atvproxy` MITM tool (https://pyatv.dev/documentation/atvproxy/) are the best available ground truth, since pyatv is MIT-licensed and can be read/ported directly. This is the single highest reverse-engineering-risk item in the whole project, precisely because there is no spec and essentially no prior art outside pyatv itself and one Swift app.
3. **A unified multi-protocol facade in Rust** (i.e., "one Rust crate that speaks DMAP+MRP+Companion+AirPlay/RAOP the way pyatv's Python `atv` object does, picking the right protocol per capability"). Every Rust project surveyed is single-protocol (AirPlay-only, or HAP-only). Building this facade — including pyatv's protocol-negotiation/capability-fallback logic (e.g., prefer Companion for remote control if available, fall back to MRP, use DMAP only for legacy tvOS versions) — is itself unprecedented in Rust and is really the core differentiator of this whole project versus the existing single-purpose Rust AirPlay crates.
4. **An AirPlay-2-tunneled-MRP transport** (MRP-over-AirPlay, the mechanism modern Apple TVs use to carry remote-control traffic inside an AirPlay session rather than a bare MRP TCP socket) has no Rust precedent found; even pyatv's own handling of this is relatively recent/evolving, so expect to track pyatv's `master` branch closely (not just a pinned release) for this specific piece, since it is one of the more actively-changing corners of the protocol per pyatv's issue tracker activity.
5. **DMAP is comparatively low-risk** — it is the oldest, best-documented (HTTP + simple binary TLV) protocol in the suite, and while no dedicated Rust crate was found, its simplicity (versus MRP/Companion/AirPlay2) means it is not a genuine research gap so much as routine implementation work once pyatv's DMAP module is used as a reference.

Everything GPL/LGPL in this survey should inform architecture and test-vector expectations only, never source text.

## Open questions

- What is this project's target license (MIT/Apache-2.0 dual, matching pyatv and the Rust ecosystem norm, or something else)? This determines whether `shairplay-rust` (LGPL) can even be considered as an optional dependency versus purely a design reference — needs an explicit decision before any AirPlay receiver-side code is written.
- Is a receiver role (accepting AirPlay streams, the shairplay-rust/shairport-sync/UxPlay niche) actually in scope for this project, or is the scope client/controller-only (matching pyatv's own primary focus of *controlling* Apple TVs and *sending* audio, not receiving mirrored screens)? This materially changes which prior art is load-bearing (RAOP-sender + MRP + Companion client code vs. full AV receiver + codec/decode stack).
- Does the project need AirPlay video/mirroring at all, or only audio (RAOP) + remote control (MRP/Companion) + metadata (DMAP/MRP)? pyatv itself treats video mirroring as out of scope for the most part; confirm before investing in H.264/H.265 decode planning inspired by UxPlay's GStreamer approach.
- Is legacy AirPlay 1 / FairPlay authentication actually required for any target device class, or can it be deprioritized entirely in favor of AirPlay 2's HAP-based pairing? Given the legal/technical risk flagged in §3, an explicit decision to defer or drop FairPlay would meaningfully de-risk the project.
- What is the actual current state of pyatv's MRP-over-AirPlay-tunnel handling on `master` as of implementation time (it was flagged above as actively evolving) — this needs a fresh read of pyatv source immediately before implementation starts, not just this report's snapshot.
- Should the project depend on `mdns-sd` directly, or wrap it behind a trait to allow swapping to a native-Bonjour path (`astro-dnssd`/`zeroconf`) later for macOS coexistence with `mDNSResponder`? shairplay-rust's precedent (mdns-sd on Linux, astro-dnssd on macOS) suggests this may eventually matter, but there is no evidence yet that pure `mdns-sd` fails to coexist with a running Bonjour daemon on macOS — needs empirical verification, not just precedent-following.
- Is there a current, authoritative copy of Apple's non-commercial HomeKit Accessory Protocol Specification PDF that should be treated as the canonical source for exact TLV8 tag numbers and the full M1–M6 pair-setup/pair-verify message tables? This report found a third-party forum mirror but could not verify it is the latest revision — obtain and pin a verified copy before implementing the pairing state machine.
- `node-appletv-remote` (multi-protocol Node client spanning AirPlay2+MRP+Companion) was surfaced but not deep-dived — worth a dedicated follow-up pass, since if it's genuinely more current/complete than the older node-appletv-x, it could be a second MIT-licensed reference alongside pyatv for the control-protocol layer.
