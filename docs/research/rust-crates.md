# Rust crate selection for a pyatv reimplementation

Research date: 2026-08-24. All versions below were verified live against the crates.io registry API (`https://crates.io/api/v1/crates/<name>`) on this date, not recalled from training data. Where a crate's maintenance status mattered, I pulled its full version history (`/versions`) to check publish cadence, and where its API shape mattered, I pulled docs.rs. Where pyatv's own protocol behavior mattered, I read the actual source on `postlund/pyatv` at `master` via the GitHub raw/API endpoints (not from memory), and I cite the exact files below. Toolchain target: rustc 1.93.1 stable, Rust 2024 edition.

This report only covers crate/ecosystem selection, per the assigned scope. It does not cover architecture, module layout, or the full protocol/message design — that belongs in later pipeline stages (Architecture, TechSpec).

## 1. Async runtime: tokio, and the sans-io question

Verified current version: **tokio 1.53.1**, published 2026-07-20, on crates.io (`https://crates.io/crates/tokio`). Tokio is by far the dominant async runtime in the Rust ecosystem (900M+ all-time crates.io downloads) and is the de facto standard for anything doing TCP/UDP networking, which this project needs heavily (mDNS multicast UDP, TCP for MRP/AirPlay/RAOP/Companion, RTP over UDP for audio).

For a **library** crate (as opposed to a top-level binary like an `atvremote` equivalent), tokio's own docs (`https://docs.rs/tokio/latest/tokio/`) explicitly warn against enabling the `full` feature flag: "As a library author your goal should be to provide the lightest weight crate that is based on Tokio... you should ensure that you only enable the features you need." The documented minimal set for a library that spawns tasks and uses `TcpStream` is `["rt", "net"]`. For this project's core protocol crate(s), recommend enabling only: `rt`, `net`, `sync`, `time`, `io-util`, and `macros` (for `#[tokio::test]` in dev-dependencies only — `#[tokio::main]` belongs in the binary crate, not the library). `codec` functionality (`Encoder`/`Decoder`/`Framed`) does **not** live in tokio itself — it's in the separate `tokio-util` crate (verified current version **0.7.19**, published 2026-07-21, same `tokio-rs/tokio` repo). Only the top-level `atvremote`-equivalent binary crate should pull `tokio = { features = ["full"] }` or a curated `rt-multi-thread` set plus whatever the CLI needs.

**Sans-io**: yes, protocol cores should be runtime-independent, and this is a well-established pattern in the Rust networking community as of 2024–2026, not a fringe idea. The core principle (originating in the Python community, adopted widely in Rust) is: state machines that parse bytes in and produce bytes/events out should not touch a socket, a runtime, or `async` at all — I/O is a thin adapter layered on top. Firezone's engineering blog has a widely cited writeup on exactly this pattern applied to Rust networking (`https://www.firezone.dev/blog/sans-io`, July 2024), and it's discussed at length on the Rust community (Hacker News thread `https://news.ycombinator.com/item?id=40872020`, "Sans-IO: The secret to effective Rust for network services"). Concretely for this project: the MRP protobuf framing/state machine, the HAP/MRP pairing (SRP + ChaCha20-Poly1305) state machine, the RTSP/AirPlay message layer, and the RAOP RTP packetizer should each be plain synchronous Rust types with methods like `fn feed(&mut self, bytes: &[u8]) -> Vec<Event>` / `fn poll_transmit(&mut self) -> Option<Bytes>`, independent of tokio. A thin `tokio`-based adapter crate then wires these sans-io cores to real `TcpStream`/`UdpSocket` I/O via `tokio_util::codec::Framed` or manual read/write loops. This buys: unit-testability without a runtime (fast, deterministic tests, good fit for `insta` snapshot tests — see §11), and the option to reuse the protocol cores under a different runtime (e.g. `smol`, or a WASM/embedded target) later without a rewrite.

## 2. mDNS / zeroconf discovery and publishing

Requirement: browsing + resolving now, publishing later, both unicast and multicast, zero C dependencies.

Verified candidates, all checked on crates.io on 2026-08-24:

- **mdns-sd** — max stable version **0.21.0**, published 2026-08-12 (i.e. 12 days before this research date — actively maintained; version history shows releases roughly every 2–4 weeks throughout 2026: 0.20.0 on 2026-05-25, 0.20.1–0.20.3 through July, 0.21.0 in August). Description on crates.io: "mDNS Service Discovery library with no async runtime dependency." Repository `https://github.com/keepsimple1/mdns-sd`, docs at `https://docs.rs/mdns-sd`.
- **searchlight** — max stable version **0.3.2**, last published 2023-09-26 — **stale**, no releases in ~3 years as of this research date. Disqualify on maintenance grounds alone.
- **libmdns** — max stable version **0.10.1**, published 2025-09-06 (reasonably fresh, used in production by `librespot`). But it is a **responder/publisher only** — it answers queries for services it owns; it has no browsing/query-sending API. Repository `https://github.com/librespot-org/libmdns`.
- **zeroconf** (zeroconf-rs) — max stable version **0.18.0**, published 2026-04-07, fairly active. But per its own README (fetched directly, `https://github.com/windy1/zeroconf-rs`): it "wraps underlying ZeroConf/mDNS implementations such as Bonjour or Avahi" — it is an FFI wrapper, requiring `libavahi-client-dev` on Linux and Bonjour/mDNSResponder on Windows/FreeBSD. This is exactly the C-dependency this project needs to avoid. **Disqualified** by the stated "no C deps" requirement.

**Recommendation: `mdns-sd` 0.21.0** for both browsing/resolving now and publishing later — it is the only pure-Rust, actively-maintained, no-C-deps candidate that does both browse (`ServiceDaemon::browse(service_type) -> Receiver<ServiceEvent>`) and register/publish (`ServiceDaemon::register(ServiceInfo)`). API surface (from docs.rs, `https://docs.rs/mdns-sd`): `ServiceDaemon` is the core handle (spawns its own background thread, not tokio-coupled — it communicates via `flume` channels that support both blocking `recv()` and `.recv_async()`, so it composes fine with a tokio-based caller without pulling tokio into `mdns-sd` itself); `ServiceInfo` describes a service to register; `ServiceEvent` is the enum of discovery events. It implements RFC 6762 (mDNS) and RFC 6763 (DNS-SD). MSRV is 1.70 per its README, well under the project's 1.93.1 toolchain. Supports IPv4 and IPv6, and runs on macOS/Linux/Windows.

**Gap — unicast**: `mdns-sd` is **multicast-only for outbound queries**. It does implement the RFC 6762 §5.4 "reply unicast to non-5353-source-port queriers" behavior on the *responder* side (tracked as GitHub issue `#469` on `keepsimple1/mdns-sd`), but it has no API to actively *send* a unicast query to a specific known host IP. This matters because pyatv supports scanning specific hosts directly (its `pyatv/support/knock.py` "knock" mechanism opens/closes raw TCP connections to wake sleeping Bonjour-proxied devices, and pyatv's core scan flow can be pointed at explicit IPs). If the Rust port needs true unicast mDNS queries against a known IP:5353 (bypassing the multicast group), `mdns-sd` alone won't do it — recommend either (a) opening a second, manually-managed `UdpSocket` and hand-rolling the unicast DNS query/response using **hickory-proto** (verified **0.26.1**, published 2026-05-01, `https://github.com/hickory-dns/hickory-dns`) purely for its `Message`/`Record` wire encode/decode types (it's a maintained fork/successor of the old `trust-dns-proto`, which is itself stale at **0.23.2**, last published 2023-10-23 — do not use `trust-dns-proto`), or (b) vendoring a small hand-rolled DNS message codec, since the wire format needed (a handful of PTR/SRV/TXT/A/AAAA record types) is small and static. Flag this as a design decision for the Architecture/TechSpec stage, not something to resolve purely by crate choice.

Do **not** use `zeroconf-rs` even though its API is arguably nicer — the C-dependency disqualification is a hard requirement per the prompt, and it also means it cannot compile confidently in a minimal container without Avahi dev headers.

## 3. Protobuf: prost + prost-build, and protoc vs protox

Verified: **prost 0.14.4** and **prost-build 0.14.4**, both published 2026-06-07 (same release, same repo `https://github.com/tokio-rs/prost`), from the `tokio-rs/prost` project (note: despite the repo living under the `tokio-rs` GitHub org, prost has no runtime dependency on tokio itself — it's a pure codec).

pyatv's MRP protocol has a large, real `.proto` corpus: I confirmed via the GitHub contents API (`https://api.github.com/repos/postlund/pyatv/contents/pyatv/protocols/mrp/protobuf`) that there are **77 `.proto` files** under `pyatv/protocols/mrp/protobuf/` (e.g. `ProtocolMessage.proto`, `DeviceInfoMessage.proto`, `CryptoPairingMessage.proto`, `NowPlayingInfo.proto`, `PlaybackQueueRequestMessage.proto`, `SendCommandMessage.proto`, etc. — 77 files total by exact count on 2026-08-24). This is a non-trivial codegen job; whatever crate builds these needs to be robust and low-friction in CI.

Two ways to compile them: (1) the traditional `protoc` (the C++ Protocol Buffers compiler) invoked by `prost-build`, requiring the `protoc` binary to be installed/available on `PATH` or pointed to via the `PROTOC` env var — an external, non-Rust, version-sensitive build dependency; or (2) **protox**, verified version **0.9.1**, published 2025-12-02, "A rust implementation of the protobuf compiler" (`https://github.com/andrewhickman/protox`, docs `https://docs.rs/protox`). protox's crates.io metadata declares `prost ^0.14.0` and `prost-reflect ^0.16.0` as dependencies, confirming compatibility with the currently-verified prost 0.14 line. Usage pattern confirmed from docs.rs: `let file_descriptors = protox::compile(["root.proto"], ["."]).unwrap(); prost_build::compile_fds(file_descriptors).unwrap();` — i.e. protox parses/compiles the `.proto` set into `FileDescriptorSet`s natively in Rust and hands them to `prost-build`'s `compile_fds`, entirely skipping the `protoc` binary. It also integrates with `miette` for readable compile errors and can feed `tonic-build`.

**Recommendation**: use `protox` 0.9.1 to compile pyatv's 77 `.proto` files, driven from `build.rs`, feeding `prost-build` 0.14.4 for codegen. This removes an entire class of "works on my machine but not in CI/Docker/cross-compile" bugs caused by `protoc` version skew (a real, common pain point with prost-based projects historically) and keeps the whole toolchain pure-Rust, matching the project's stated preference for no C deps elsewhere. Only fall back to real `protoc` if protox chokes on some pyatv-specific `.proto` syntax (e.g. custom options) — this should be verified empirically once the actual `.proto` files are vendored into the repo, since protox does not claim 100% feature parity with every obscure protoc extension.

## 4. Binary plist: the `plist` crate

Verified current version: **plist 1.10.0**, published 2026-07-04, repository `https://github.com/ebarnard/rust-plist/`, description "A rusty plist parser. Supports Serde serialization," 58M+ all-time downloads (very widely used, low risk).

Confirmed via docs.rs (`https://docs.rs/plist/latest/plist/`) that it supports all three plist formats: binary (`bplist00` — functions `to_file_binary`, `to_writer_binary`, and the corresponding readers), XML, and ASCII/OpenStep (`from_reader_ascii`). It offers both an in-memory `Value` enum API (dictionary-style access via `as_dictionary()`/`get()`) and full `serde` `Serialize`/`Deserialize` derive integration via an optional `serde` feature — i.e. you can deserialize a binary plist blob straight into a typed Rust struct with `#[derive(Deserialize)]`, matching how pyatv itself round-trips typed dicts through `plistlib` in Python.

This directly matters for AirPlay/RAOP: pyatv's `pyatv/support/rtsp.py` defines `BPLIST_CONTENT_TYPE = "application/x-apple-binary-plist"` and its HTTP layer (`pyatv/support/http.py`) has an explicit `decode_bplist_from_body` path — AirPlay devices routinely send/receive binary-plist request/response bodies over RTSP-flavored HTTP (e.g. `/info`, `/pair-setup`, `/pair-verify`, playback control payloads). `plist` 1.10.0 with the `serde` feature enabled is the correct fit: read the raw HTTP body bytes, hand them to `plist::from_bytes::<T>()` (or the `Value` API when the schema is dynamic/unknown), and mirror that on the write path with `plist::to_writer_binary`.

## 5. Why reqwest/hyper don't fit AirPlay's HTTP/RTSP, and what a custom codec needs

I read pyatv's own hand-rolled implementation to ground this rather than assume it: `pyatv/support/http.py` and `pyatv/support/rtsp.py` on `postlund/pyatv` master.

Confirmed facts from `http.py`:

- pyatv implements its **own** HTTP request/response formatter and parser from scratch (`_format_message`, `_parse_http_message`, `format_request`/`parse_request`, `format_response`/`parse_response`) rather than using Python's `http.client` or an HTTP framework for this traffic.
- Critically, `parse_request` and `parse_response` are **both implemented and both used on the same connection** — i.e. the same TCP socket carries HTTP-like request framing in *both directions*: pyatv sends requests and parses responses (normal client role), but it also **parses incoming requests** on that connection (`HttpRequest` type, `parse_request` function used server-side) because AirPlay/RAOP receivers open a reverse/event channel back to the controller over HTTP-like framing on the existing or a companion TCP connection. A conventional HTTP client library (reqwest, hyper's client half) has no concept of "also be the server on this same socket" — it assumes a strict client role talking to a server that only ever sends responses.
- The message framing itself is non-standard: methods aren't restricted to the standard HTTP verb set — `pyatv/support/rtsp.py` uses RTSP methods (`ANNOUNCE`, `SETUP`, `RECORD`, `FLUSH`, `TEARDOWN`, `SET_PARAMETER`, `GET_PARAMETER`, `OPTIONS`, `POST`) over what is nominally `RTSP/1.0` or `HTTP/1.1` framing depending on device generation, with `USER_AGENT = "AirPlay/550.10"` and bodies that are frequently binary plist (`application/x-apple-binary-plist`) rather than the JSON/form bodies HTTP client crates are built around.
- Body framing relies on `Content-Length` with no chunked-transfer-encoding handling visible in pyatv's parser, and the parser explicitly buffers until `Content-Length` bytes are available (`if len(body or []) < content_length: return None, ..., message` — i.e. "not enough data yet, wait for more"), which is exactly the incremental/partial-frame behavior a `tokio_util::codec::Decoder` is designed to express (`Ok(None)` = need more bytes).
- pyatv's RTSP layer hand-builds SDP bodies (the `ANNOUNCE_PAYLOAD` template with `v=0`/`o=`/`s=`/`c=`/`t=`/`m=`/`a=rtpmap`/`a=fmtp` lines) as raw strings, and does MD5-based Digest auth (`from hashlib import md5`) manually rather than through a generic HTTP auth middleware.

None of `reqwest` (client-only, high-level, assumes standard HTTP semantics, does not expose raw framing) or `hyper` (lower-level but still fundamentally a client-*or*-server-per-connection model, not "read/write arbitrary framed messages bidirectionally on one raw `TcpStream`") fit this. `h2` (HTTP/2, verified **0.4.19**, published 2026-08-24 — i.e. same-day as this research, very actively maintained) and `httparse` (verified **1.10.1**, published 2025-03-03, "a tiny, safe, speedy, zero-copy HTTP/1.x parser") are also not the right layer: `httparse` only parses the standard HTTP/1.x request/status-line grammar, and AirPlay's RTSP status line (`RTSP/1.0 200 OK`) and non-standard methods are close enough to trip up a strict parser's assumptions in some implementations, and it still gives you no help with the bidirectional-same-socket and binary-plist-body concerns.

**Recommendation**: build a small custom `tokio_util::codec::Decoder`/`Encoder` pair (using `tokio-util` 0.7.19, `BytesMut`-based) that: (1) scans for the `\r\n\r\n` header/body boundary, (2) parses a generic first line permissively (method/URI/protocol-version *or* protocol-version/status-code/reason, trying both, exactly mirroring pyatv's own dual `parse_request`/`parse_response` approach — the wire format is genuinely the same grammar read from either direction), (3) uses `Content-Length` to buffer the body and returns `Ok(None)` for partial frames, (4) exposes an enum `Frame::Request(...) | Frame::Response(...)` so a single `Framed<TcpStream, AirplayCodec>` can be `.next()`'d for both outbound-request's-response and inbound server-role requests on the same socket, and (5) treats `application/x-apple-binary-plist` bodies as opaque `Bytes` at the codec layer, decoding them with `plist` (§4) one layer up. This is squarely a case for the sans-io pattern from §1: the message-framing logic (steps 1–4) should be testable with plain byte slices with no `tokio_util` or socket involved, and the `Decoder`/`Encoder` impl is just a thin wire-up.

## 6. OPACK

There **is** a dedicated crate: **apple-opack**, verified version **1.0.0**, published 2026-07-22 (i.e. **about one month old** as of this research date — very new), repository `https://gitlab.com/clicker-devs/apple-opack.git`, MIT license, single maintainer on crates.io. Confirmed via docs.rs (`https://docs.rs/apple-opack`): API is `pack()`/`unpack()`, a `Value` enum for the recursive OPACK value model, an `Error` type, and an `opack_dict!` convenience macro; both encoder and decoder support OPACK's back-reference/deduplication mechanism, though — per the crate's own documented design note — the encoder dedups by raw encoded bytes while the decoder dedups by value, an intentional asymmetry the docs say mirrors "the undocumented Python reference implementation," i.e. it appears to have been written by directly porting pyatv's own OPACK code. Documentation does not explicitly confirm UID-reference or absolute-time (tag `0x06`) support.

For grounding, I read pyatv's actual OPACK implementation, `pyatv/support/opack.py` (`https://github.com/postlund/pyatv/blob/master/pyatv/support/opack.py`). It is small (roughly 150–200 lines) and its own module docstring is explicit about its gaps: "Absolute time (0x06) is not implemented (can unpack as integer, not pack)... Pack implementation does not implement UID referencing... Likely other cases missing." The tag layout confirmed directly from source: `None` → `0x04`, `bool` → `0x01`/`0x02`, `UUID` → `0x05` + 16 raw bytes, small ints `< 0x28` → `value + 8` (single byte), larger ints get a `0x30`/`0x31`/`0x32`/`0x33` prefix byte followed by 1/2/4/8 little-endian bytes depending on magnitude (or an explicit size hint to force a wider encoding on re-pack).

**Recommendation**: given `apple-opack` is only ~1 month old with a single maintainer and an unverified production track record, treat it as a strong *reference/starting point* rather than a blind dependency pin — either (a) vendor/fork it under this project's own control so you're not exposed to an unmaintained-crate risk on a protocol this central (OPACK carries HAP pairing and Companion-link payloads), or (b) reimplement directly from pyatv's own `opack.py` as ground truth, which is small enough (~150 lines of Python) that a faithful Rust port is a half-day task and gives full control over the known gaps (absolute time, UID refs) that both pyatv and `apple-opack` currently leave unhandled. Either way, budget explicit test vectors captured from real device traffic (or ported from pyatv's own OPACK test fixtures, if any exist in its test suite) rather than trusting either implementation blindly, since this is a reverse-engineered, Apple-undocumented format.

## 7. Audio for the RAOP sender

I read pyatv's actual RAOP sender code to determine what's really needed, rather than assuming ALAC encoding is required:

- `pyatv/support/rtsp.py` defines the SDP body pyatv sends in its `ANNOUNCE` request: `ANNOUNCE_PAYLOAD` includes `m=audio 0 RTP/AVP 96` and, critically, **`a=rtpmap:96 L16/44100/2`** — `L16` is the standard RTP payload name for raw 16-bit linear PCM, *not* ALAC. The accompanying `a=fmtp:96 {FRAMES_PER_PACKET} 0 {bits_per_channel} 40 10 14 {channels} 255 0 0 {sample_rate}` line follows ALAC's conventional `fmtp` field layout (frames-per-packet, compatible-version, bits-per-sample, etc.) even though the codec named in `rtpmap` is `L16`. `FRAMES_PER_PACKET = 352` is a module constant.
- `pyatv/protocols/raop/parsers.py`'s `get_audio_properties()` reads the receiver's advertised mDNS TXT-record keys **`sr`** (sample rate, default 44100), **`ch`** (channels, default 2), and **`ss`** (sample size in bits, default 16) to determine what to send — i.e. sample-rate/channel/bit-depth negotiation is driven by the `_raop._tcp`/`_airplay._tcp` TXT records discovered over mDNS, not hardcoded.
- I found **no reference to ALAC encoding** anywhere in `pyatv/protocols/raop/` (`stream_client.py`, `packets.py`, `protocols/airplayv1.py`, `protocols/airplayv2.py` — grepped all for `alac`/`codec`/`payload`/`fmtp`/`L16`, only the `rtsp.py` SDP template matched). This strongly suggests pyatv's current RAOP sender streams **raw/linear PCM**, not ALAC-compressed audio, for the codepaths I inspected.
- For decoding arbitrary input media into PCM to feed the sender, pyatv's `pyatv/protocols/raop/audio_source.py` imports and uses **`miniaudio`** (a Python binding around C `miniaudio`/`libminimp3`/`dr_libs`) to turn MP3/FLAC/WAV/etc. into raw PCM frames it then streams.

Given that: an ALAC **encoder** may not even be a hard requirement for parity with pyatv's current sender behavior (raw PCM appears sufficient for the paths inspected) — this should be confirmed against a live device capture before committing engineering time to ALAC encoding, and is flagged as an open question below. If ALAC encoding does turn out to be needed (e.g. for bandwidth reasons, or because some AirPlay 2 receivers reject/deprioritize raw-PCM RAOP streams), the crate landscape is thin:

- **alac-encoder**, verified version **0.3.0**, but last published **2022-01-10** — over 4 years stale as of 2026-08-24 (confirmed via full version history: 0.1.0/0.1.1 in 2019, 0.2.0 in 2021-10, 0.3.0 in 2022-01, nothing since). Docs.rs shows 0% documentation coverage. It is described as "a Rust port of Apple's open source ALAC library," i.e. a real encoder (not a stub), but unmaintained. ALAC as a bitstream format is frozen/stable (Apple open-sourced it once, long ago, and it hasn't changed), so "unmaintained but functionally complete" is a defensible risk profile here — but plan to vendor/fork it into this project's repo rather than depend on an upstream that could disappear from crates.io or bitrot against a future Rust edition.
- **symphonia-codec-alac** (part of the `symphonia` project, verified **0.6.1**, same release train as `symphonia` core, published 2026-08-13) is **decode-only** — it lets you read ALAC, not produce it, so it doesn't help the sender side (encoding), only a hypothetical receiver/decoder side.
- No other actively maintained pure-Rust ALAC encoder was found on crates.io as of this search (queries for "alac encoder" and "apple lossless" turned up `symphonia-codec-alac` (decode only), `alac-encoder` (stale), and otherwise unrelated crates like `coreaudio`, `rockbox-codecs`, and various media-transcoding tools not focused on ALAC specifically).

For **decoding input media** (the pyatv `miniaudio` equivalent, needed regardless of whether the sender re-encodes to ALAC or streams PCM): **symphonia**, verified current version **0.6.1**, published 2026-08-13, pure-Rust, MPL-2.0 licensed (note: MPL-2.0 is weak/file-level copyleft — worth a licensing sanity check against this project's overall license choice, but does not require the whole project to be MPL). Confirmed feature-flag structure directly from its `Cargo.toml` on the `pdeljanov/Symphonia` repo: default features are `["adpcm", "flac", "mkv", "ogg", "pcm", "vorbis", "wav"]` (royalty-free formats only, by design); non-default opt-in features include `mp3` (`symphonia-bundle-mp3/mp3`), `aac` (`symphonia-codec-aac`), `alac` (`symphonia-codec-alac`), `isomp4`, `caf`, `aiff`; an `all` feature turns on everything. For this project, enable at minimum `mp3`, `aac`, `wav`, `flac`, `ogg`, `alac` to cover the realistic set of input media users will hand to a `push_updates`/stream-file style API.

**Sample-rate handling**: since the receiver dictates its required sample rate via the mDNS `sr` TXT key (commonly 44100 but not guaranteed), and input media will arrive at whatever rate it was encoded at, a resampler is needed in the pipeline. Recommend **rubato**, verified current version **5.0.0**, published 2026-08-10, pure-Rust, "asynchronous resampling library intended for audio data" (`https://github.com/HEnquist/rubato`) — actively maintained, no C deps, fits directly between symphonia's decoded PCM output and the RTP packetizer's expected sample rate.

**Opus and AirPlay 2**: I found no evidence Opus is part of the AirPlay/RAOP codec set. Per web research (AirPlay 2 realtime-audio sender writeups and community documentation), AirPlay 2's realtime audio stream type (type 96) and buffered stream type (type 103) both center on **ALAC** and, per one community source, RAOP historically also supports **AAC**/**AAC-ELD** and plain **PCM**; Opus was not mentioned by any source checked. Apple Music's own lossless-to-AirPlay path reportedly transcodes ALAC → AAC 256kbps for transmission in some cases, again not Opus. **Recommendation: do not budget for Opus support** — it appears to be irrelevant to this protocol family; the `opus` crate (verified **0.4.0**, published 2026-08-23, "safe Rust bindings for libopus") and `audiopus` (verified **0.2.0**, stale since 2021-04-22) are both FFI wrappers around the C `libopus` anyway, so they'd also violate the "no C deps" preference expressed elsewhere in this research if they were ever needed. Treat Opus as out of scope unless a specific AirPlay 2 device/feature is later found to require it.

**cpal** (verified **0.18.2**, published 2026-08-16, cross-platform audio I/O) is likely **not needed** for the core sender — pyatv streams from files/URLs via a decoder (symphonia), not from live microphone/system-audio capture — but keep it in mind as an optional add-on crate if a future feature needs to capture live system audio to AirPlay-cast it (out of scope for the current pyatv parity target as far as I can tell from the source read).

## 8. Serde ecosystem

Verified current versions on crates.io: **serde 1.0.229** (published 2026-07-18) and **serde_json 1.0.151** (published 2026-07-20), both from `serde-rs` (`https://github.com/serde-rs/serde`, `https://github.com/serde-rs/json`). Both are foundational, extremely stable (serde has been on major version 1.x for years), and both are already implied as transitive needs by `plist`'s serde feature (§4) and by config/CLI concerns. ## 9. Error handling: thiserror

Verified current version: **thiserror 2.0.20**, published 2026-08-08 (very recent — 16 days before this research date), `https://github.com/dtolnay/thiserror`. Confirmed via version history that the crate is on **major version 2** (2.0.16 through 2.0.20 all published within the last ~12 months as of this check, i.e. actively maintained with frequent patch releases). thiserror 2.x's derive API is materially the same shape as 1.x for the common case (`#[derive(Error)] enum MyError { #[error("...")] Variant(...) }`) but added generic-error-source improvements over 1.x; make sure any example code or docs referenced during implementation targets the 2.x API, not 1.x (training-data staleness risk explicitly flagged here since thiserror 1.x was still common in many older tutorials). Recommend thiserror for leaf error types in each protocol module, and consider a lightweight `anyhow`-free design at the library boundary (return concrete `thiserror`-derived enums from the public API of a library crate; `anyhow` is more appropriate inside the `atvremote`-equivalent binary's own error handling, not in library crates that other consumers will match on).

## 10. Logging/tracing

Verified current versions: **tracing 0.1.44** (published 2025-12-18) and **tracing-subscriber 0.3.23** (published 2026-03-13), both from the `tokio-rs/tracing` repo. This is the standard structured-logging/instrumentation crate for async Rust and pairs naturally with tokio (§1) — spans/events correctly track across `.await` points, which a plain `log`-crate-based approach does not handle well in async code. Recommend `tracing` in library crates (protocol cores emit `tracing::debug!`/`trace!` events; sans-io cores, per §1, can still emit tracing events without depending on tokio itself — `tracing` has no runtime dependency), and `tracing-subscriber` (with the `env-filter` feature) wired up only in the binary crate to actually render output, following the standard "libraries emit, binaries subscribe" tracing convention.

## Open questions

- Does pyatv's RAOP sender actually need ALAC encoding for parity, or is raw-PCM (`L16`) sufficient for all target device generations? The source I read (`pyatv/support/rtsp.py`'s `ANNOUNCE_PAYLOAD`) suggests raw PCM is what's currently sent, but this should be verified against a live capture against a current-generation Apple TV/HomePod before deciding whether to invest in vendoring the stale `alac-encoder` crate — this materially changes §7's implementation cost.
- Is `apple-opack` (1.0.0, published 2026-07-22) trustworthy enough to depend on directly, or should OPACK be reimplemented in-house from pyatv's own `opack.py` as ground truth? It's extremely new (about a month old at research time) with a single maintainer and an unusual encoder/decoder deduplication asymmetry documented in its own README — worth a closer code read (not just docs) before committing.
- What's the right approach for unicast mDNS host-scanning (pyatv's explicit-host scan / Bonjour-sleep-proxy "knock" use case), given `mdns-sd` only sends multicast queries? Options: hand-rolled `UdpSocket` + `hickory-proto` wire types, or a from-scratch minimal DNS message codec (the actual record-type surface needed — PTR/SRV/TXT/A/AAAA — is small). This needs an architecture decision, not just a crate pick.
- protox 0.9.1's claimed protoc compatibility should be validated empirically against the real, vendored pyatv `.proto` corpus (77 files) once available in-repo — the crate doesn't claim 100% feature parity with every protoc extension, and pyatv's `.proto` files haven't been checked file-by-file for anything protox-unfriendly (e.g. custom FileOptions, `syntax = "proto2"` vs `proto3` mixes, if any).
- `mdns-sd`'s publish/registration path (needed "later" per the requirement) hasn't been evaluated for feature completeness against what this project will eventually need to *advertise* (e.g. publishing an `_mediaremotetv._tcp` or Companion-link service for a pairing flow) — the research here focused mainly on the browse/resolve side since that's the near-term need; revisit before the publish milestone.
- No crate research was done in this pass on the cryptography needed for HAP/MRP pairing (SRP6a, Curve25519/X25519, Ed25519, ChaCha20-Poly1305) or on QUIC (AirPlay 2 can use it in some paths) — those are out of this report's assigned scope (runtime/networking/serialization/codecs) but will need their own crate-verification pass (candidates like `RustCrypto`'s `chacha20poly1305`, `x25519-dalek`, `ed25519-dalek`, and an SRP implementation should be checked with the same rigor as above, not assumed from memory).
